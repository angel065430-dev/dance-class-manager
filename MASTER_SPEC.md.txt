# MASTER_SPEC.md

# Dance Class Manager

## Master Product Specification

**Project Name:** Dance Class Manager
**Project Type:** Multi-user Web Application
**Primary Language:** Traditional Chinese
**Business Timezone:** Asia/Taipei
**Current Architecture:** Vue 3 + TypeScript + Vite + Tailwind CSS + Supabase + Vercel

---

# 1. Project Overview

建立一個正式的舞蹈課程管理系統，主要用於 Zumba 課程管理。

系統必須同時提供：

1. 學員前台
2. 學員專區
3. 老師／管理員後台

系統不是單一 HTML Demo，也不是 LocalStorage 系統。

所有正式業務資料必須儲存在 Supabase PostgreSQL，並支援多使用者與多瀏覽器即時同步。

---

# 2. Core Business Goals

系統主要解決以下問題：

* 課程報名
* 整期報名
* 多班整期報名
* 單堂課報名
* 假日快閃／特別活動課報名
* 多堂特別課優惠
* 優惠碼
* 收款管理
* 請假
* 銷假
* 補課
* 補課審核
* 學員管理
* 運動中心學生管理
* 動態補課名額
* 每堂課不同的門禁密碼
* 點名
* 即時名額同步

所有使用者在不同：

* 瀏覽器
* 手機
* 電腦
* 裝置

開啟系統時，都必須以 Supabase 中央資料庫為準。

不得出現：

> 同一個瀏覽器修改後看起來正常，但其他瀏覽器仍然看到舊資料。

# 4. Authentication and Login

## 4.1 Student Login

學生需要有簡單的登入方式。

預期使用：

* 手機號碼作為主要識別資訊

實際登入技術必須與 Supabase Auth 安全架構相容。

不得：

* 將 PIN 明碼直接存入前端
* 使用 LocalStorage 作為正式身分驗證
* 使用前端假登入作為正式安全機制

學生重新整理頁面後，登入狀態應正常維持。

---

## 4.2 Admin Login

管理員登入必須使用正式、安全的身份驗證。

不得：

* 在前端硬編碼管理員密碼
* 使用 Logo 連點作為真正的安全機制
* 只靠隱藏網址保護後台

管理員權限必須由：

* Supabase Auth
* Role
* Row Level Security

共同控制。

# 8. Full-Term Registration

學生可以報名整期課程。

重要規則：

* 整期報名者可以一次報名多個班級。
* 系統應支援將多個整期班級加入同一筆訂單。
* 每個班級的資格與名額必須獨立驗證。

---

## 8.1 Halfway Registration Rule

常態班可以設定：

> 課程進行超過一半後，停止整期報名。

此規則預設為啟用。

計算方式應根據：

* 已完成課堂數
* 總課堂數

判斷。

當已完成課堂數達到規定比例後：

* 停止整期報名
* 如該課程允許，學生仍可以報名單堂課

---

# 9. Single-Session Registration

學生可以報名單堂課。

支援：

* 選擇一堂或多堂
* 同一訂單內報名多個日期

單堂課與整期課的資格必須分開管理。

# 15. Leave System

學生可以線上請假。

---

## 15.1 Leave Deadline

正常規則：

> 必須在課程開始前至少 90 分鐘完成請假。

系統必須根據：

* 實際課程開始日期
* 實際課程開始時間
* Asia/Taipei 時區

進行判斷。

---

## 15.2 Admin Manual Exception

管理員可以在特殊情況下：

* 手動建立請假
* 手動修改請假

這類操作必須留下：

* 操作者
* 時間
* 原因

稽核紀錄。

---

## 15.3 Leave Cancellation

學生可以在規則允許時取消請假。

但如果：

> 原本釋出的名額已經被其他補課學生使用。

系統必須防止造成資料矛盾。

取消請假前必須重新驗證目前名額狀態。

### 15.3.1 已確認規則（2026-09-02 業主確認，Phase 0 Round 2）

若請假所釋出的名額已被其他補課學生使用（補課預約狀態已進入 `confirmed`／`admin_approved`／`attended` 等已使用狀態）：

> 禁止學生取消請假。

系統應拒絕該取消操作並回傳明確錯誤訊息。管理員仍可透過第 15.2 節「Admin Manual Exception」機制人工介入處理特殊情況，但該操作必須留下稽核紀錄（操作者、時間、原因）。

---

# 16. Makeup Credits

符合規則的請假可能產生補課資格。

補課資格與原始請假紀錄必須有明確關聯。

---

## 16.1 Makeup Validity Window

目前正式規則：

> 補課申請日期必須在請假課程日期前後 20 天內。

也就是：

```text
Leave Date - 20 Days
至
Leave Date + 20 Days
```

超過有效期限後：

* 不可再使用該補課資格

---

# 17. Venue Isolation

補課資格預設採取：

> 場地隔離。

也就是：

* 自營教室的補課資格
* 運動中心的補課資格

預設不能互相使用。

除非未來新增明確規則。

---

# 18. Same-Class Makeup Rules

## 18.1 Full-Term Students

整期報名學生：

> 不可以使用補課資格，補到自己原本已經擁有上課資格的同一班級／同一堂。

原因是學生原本已經有該堂課的上課權利。

---

## 18.2 Single-Session Students

單堂報名學生：

> 可以在符合補課規則的情況下，申請補到同一班級的其他日期。

但不得：

* 對自己已經報名的同一堂課重複預約
* 產生重複出席資格

---

# 19. Makeup Reservation

學生可以查看符合資格的補課課程。

系統必須自動篩選：

* 在補課有效期限內
* 同一場地
* 學生尚未擁有該堂出席資格
* 尚有補課名額
* 符合班級規則

---

## 19.1 Makeup Approval

補課申請可以採取：

* 自動核准
* 管理員審核

管理員可以設定或依個案決定。

---

## 19.2 Manual Makeup Approval

如果老師知道有人臨時無法上課，即使尚未正式透過系統完成一般流程，管理員也可以：

> 手動確認／核准補課申請。

這是正式需求。

管理員手動操作時：

* 必須重新檢查名額
* 必須留下稽核紀錄
* 可以要求填寫原因

---

# 20. Makeup Confirmation

補課學生在補課前需要再次確認。

正式規則：

> 最晚必須在開課前 1 小時完成確認。

如果：

* 超過確認時間仍未確認
* 或確認後實際缺席

系統可以依商業規則將該補課資格視為已使用。

重要原則：

> 補課資格不得因未確認而無限期保留。

實際狀態流程必須明確設計。

---

# 21. Self-Operated Studio Capacity

自營教室課程需要管理：

* 整期學生
* 單堂學生
* 請假學生
* 補課學生

名額必須由資料庫最終判斷。

前端顯示的剩餘名額只能作為資訊。

---

## 21.1 Concurrency Requirement

不得使用以下不安全流程：

1. 前端讀取剩餘名額
2. 前端自行減 1
3. 直接建立報名

正式報名與補課預約必須：

* 在資料庫重新驗證
* 使用交易／RPC／適當鎖定
* 避免多人同時搶最後一個名額時超賣

---

# 22. External Center Makeup Capacity

運動中心學生不透過本系統正式報名。

因此系統無法知道實際全部學生人數。

管理員需要：

> 為每一堂課預先設定「固定基礎補課名額」。

例如：

```text
Base Makeup Capacity = 2
```

然後加上：

> 該堂課當天的請假人數。

---

## 22.1 Official Capacity Formula

運動中心某一堂課目前可補課人數：

```text
Base Makeup Capacity
+
Number of Eligible Leaves for This Session
+
Manual Adjustment
-
Reserved Makeup Seats
```

也就是：

```text
可補課名額
=
預設補課名額
+
當天請假人數
+
人工調整
-
已預約補課人數
```

---

## 22.2 Important Requirement

系統必須保留每個組成部分。

不得只存：

> 剩餘補課名額 = 5

而失去計算來源。

管理員應能看到：

* 基礎補課名額
* 當日請假人數
* 人工調整
* 已補課預約人數
* 最終剩餘名額

---

# 49. Phase 0 Confirmed Decisions Addendum（2026-09-02，Round 2）

以下為業主於 Phase 0 專案稽核階段第二輪確認的正式商業規則，補充於原條文之外，未來實作與需求變更時應以此附錄為準（詳見 `PHASE_0_AUDIT_REPORT.md` 完整分析）。依第 46 節需求變更規則記錄。

## 49.1 學生登入方式

學生登入採用 Supabase Auth 原生 Phone + Password 機制。手機號碼為識別帳號，PIN（6 位數字）對應 Supabase Auth 的密碼欄位，不使用合成 Email、簡訊 OTP 或自訂 JWT 作為登入機制。

## 49.2 PIN 規則

1. PIN 為 6 位數字。
2. 禁止過度簡單的 PIN（例如全部相同數字、連續遞增/遞減）。
3. PIN 不得以明碼存放，完全交由 Supabase Auth 密碼機制處理。
4. 忘記 PIN 第一版由管理員協助重設，不提供自助簡訊重設。

## 49.3 請假取消規則

見第 15.3.1 節：名額已被使用時禁止取消請假。

## 49.4 補課核准模式

第一版全系統預設自動核准，管理員保留手動核准／駁回／建立／調整名額的完整能力。不依場地／班級／課堂分別設定核准模式。

## 49.5 運動中心補課基礎名額

`default_base_makeup_capacity` 設定於班級層級，建立課堂時帶入預設值，管理員可對單一課堂覆蓋調整。

## 49.6 席位轉讓

系統不處理轉讓雙方之間的金流，已付款原則上不退款。系統只記錄轉讓資格、原學生、受讓學生、轉讓時間、管理員處理紀錄與完整歷史稽核。

## 49.7 管理員 MFA

學生第一版不要求 MFA。管理員帳號於一般開發階段（Phase 3）先採用 Email+Password；正式上線前的安全性複查階段，強制要求管理員帳號啟用 TOTP 兩步驟驗證。

## 49.8 CSV 匯出與行事曆整合

CSV 匯出為正式上線前必須完成項目，非 Nice-to-have。Google Calendar／ICS 行事曆整合可排在核心報名/請假/補課功能之後實作。
